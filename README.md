# نظام إدارة الموارد البشرية — HR System

تطبيق سطح مكتب لإدارة الموارد البشرية مبني بـ **Electron + React + TypeScript + Prisma**، بواجهة فاخرة داكنة (glassmorphism + soft 3D) وثنائي اللغة (عربي/إنجليزي) مع دعم كامل لـ RTL.

> **الحالة الحالية:** وحدات **إدارة المستخدمين والصلاحيات** و**الأقسام** (حالة ديناميكية) و**الموظفون** (استيراد/تصدير، ملف العمل، دوسييه، حالات بتتبع تاريخي، معاش تلقائي، عقود جديدة، وكتالوج أنواع التعاقد) و**الإجازات** (أنواع وفق القانون المصري + مستند موثق) و**الأجور والمرتبات** (رفع كشف PDF وتوزيع أظرف الموظفين تلقائيًا) مكتملة، مع لوحة قيادة HR (ملخص حي: KPI + توزيع الحالات + أعلى الأقسام + الإجازات والمرتبات) و**نسخ احتياطي شامل** (ZIP مؤرخ + استعادة)، وتحصينات أمان (قفل تسجيل الدخول وفحص توقيع الملفات). الوحدات الأخرى (الحضور والانصراف، تقييم الأداء، التوظيف، التقارير) مخططة كإضافات لاحقة — النظام مصمم من الأساس ليكون قابلاً للامتداد.
**تقرير الغيابات:** أيام الغياب مشتقّة من رأس ظرف الحافز، فتُقرأ من الملف عند الفحص وتُخزَّن على `PayrollEntry`. ولكل كشف علامة `absencesScanned` تبيّن أنه فُحص — فإن بقي كشف غير مفحوص (كشف قديم أو مستعاد من نسخة احتياطية) يفحصه التطبيق **تلقائيًا عند الإقلاع**، ويعرض تبويب الغيابات شريط تنبيه بدل جدول فارغ. التفاصيل في [المراجعة ومفردات الأجر](#المراجعة-ومفردات-الأجر).
**تقرير المعاشات:** تبويب في شاشة المراجعة يعرض المحالين للمعاش (الكود/الاسم/القسم/تاريخ الميلاد/تاريخ المعاش) مع فلتر بالسنة والشهر لمعرفة من خرج في كل شهر. تاريخ المعاش هو تاريخ بلوغ السن القانونية من تاريخ الميلاد — لا تاريخ تسجيل الحالة — فيصلح للتجميع الشهري.
**النسخ الاحتياطي** (تثبيت الإعدادات): أرشيف ZIP مؤرخ (مثال `backup-2026-10-11_14-16-38.zip`) في `<Documents>/HR-System/Backups` يشمل لقطة متسقة للقاعدة (`VACUUM INTO`) + كل مستندات الملفات (الموظفين/الإجازات/المرتبات/التدرجات/قرارات النقل/الحوافز) — إنشاء/قائمة/استعادة (تحفظ النسخة الحالية `pre-restore` بجانب القاعدة ثم يُعاد تحميل التطبيق)/حذف، بصلاحية `settings.edit`. قائمة المجلدات المشمولة مشتقّة من `DOCUMENT_FOLDERS` في `electron/main/document-folders.ts`، فأي نوع مستند جديد يُضاف هناك يُشمَل تلقائيًا.

## نظرة عامة والقرارات المعتمدة

| القرار | الاختيار |
|---|---|
| المنصة | Electron (تطبيق سطح مكتب، Windows أولاً) |
| الواجهة | React 18 + TypeScript + Vite (عبر `electron-vite`) |
| قاعدة البيانات | SQLite محلية + Prisma (تعمل في الـ main process فقط) |
| الهوية البصرية | داكن فاخر + glassmorphism + soft 3D + motion tokens |
| اللغات | العربية (RTL) افتراضياً + الإنجليزية (LTR)، تبديل فوري |
| الصلاحيات | أدوار (Roles) + صلاحيات لكل وحدة (per-module permissions) |
| أول تشغيل | حساب افتراضي جاهز (`admin` / `admin123`) |
| مستوى الـ 3D | CSS transforms + ظلال طبقية + Framer Motion (أداء خفيف) |

## المتطلبات

- **Node.js** >= 18 (مُختبر على Node 24)
- **npm** (يُستخدم package-lock.json)
- نظام Windows لتشغيل أمر التغليف `build:win`

## البدء السريع

```bash
npm install                 # يولّد عميل Prisma تلقائيًا عبر postinstall
npm run dev                 # تشغيل التطبيق في وضع التطوير
```

عند أول تشغيل يُنشئ التطبيق قاعدة البيانات تلقائياً في مجلد بيانات المستخدم، ويُجهِّز الأدوار الأساسية وحساب المدير الافتراضي:

```
اسم المستخدم: admin
كلمة المرور:  admin123
```

> **تنبيه:** غيِّر كلمة مرور المدير الافتراضي من شاشة "ملفي الشخصي" فور أول دخول في بيئة الإنتاج.

## أوامر التطوير

| الأمر | الوصف |
|---|---|
| `npm run dev` | تشغيل التطبيق الكامل (Electron + Vite) في وضع التطوير — يولّد عميل Prisma إن كان قديمًا، ويعيد بناء الـ main والـ preload تلقائيًا عند تعديلهما (`--watch`) |
| `npm run build` | بناء main + preload + renderer عبر `electron-vite build` (يولّد عميل Prisma أولًا) |
| `npm run preview` | معاينة ناتج البناء |
| `npm run typecheck` | فحص أنواع TypeScript (`tsconfig.node.json` + `tsconfig.web.json`) |
| `npm run lint` | فحص ESLint (صفر تحذيرات مسموحة) |
| `npm run prisma:generate` | توليد عميل Prisma |
| `npm run prisma:ensure` | توليد عميل Prisma فقط إذا كان لا يطابق `prisma/schema.prisma` |
| `npm run prisma:snapshot` | تحديث لقطة DDL بعد أي تعديل على `schema.prisma` |
| `node scripts/update-employee-dept-contract.mjs [--apply]` | تعبئة عمودي القسم ونوع التعاقد للموظفين من ملف Excel (معاينة افتراضياً) |
| `node scripts/reconcile-rehires.mjs [--apply]` | ربط موظفين أُضيفوا كملفات جديدة بملفاتهم الأصلية وإكمال الفراغات — تطابق بدرجات ثقة (قومي/تأميني/اسم/أسرة) |
| `node scripts/link-employee-files.mjs [--apply] [dir]` | ربط ملفات عمل خارجية بالموظفين بمطابقة اسم الملف مع كود الموظف، ونسخها باسم `<كود>_<اسم>` (معاينة افتراضياً) |
| `npm run build:win` | بناء + تغليف نسخة Windows (مجلد غير مضغوط + مثبّت NSIS) |
| `npm run payrolls:backfill` | إعادة بناء المفردات **وأيام الغياب** لكل الكشوف المخزَّنة (اسم مختصر للسكربت أعلاه) |
| `node scripts/backfill-payroll-items.mts [--dry]` | إعادة استخراج مفردات الأظرف وأيام الغياب من ملفات الكشوف المخزَّنة في فاتر قديم (يمسح بنود الدفعة ويعيد بناءها) |

### قاعدة هندسية صارمة

Prisma و bcrypt وأي كود Node يعمل **في الـ main process فقط**. الـ renderer يصل للبيانات حصرياً عبر `ipcMain.handle` + `contextBridge`، مع:

```ts
nodeIntegration: false
contextIsolation: true
```

هذا يضمن أن قاعدة البيانات وكلمات المرور لا يمكن الوصول إليها من كود الواجهة، وأن كل عملية تمر عبر طبقة الصلاحيات الموثوقة في الـ main process.

## قاعدة البيانات

المخطط في `prisma/schema.prisma` يحتوي على عشرين نموذجًا:

- **User** — المستخدمون (اسم المستخدم، البريد، الاسم الكامل، hash كلمة المرور، الدور، الحالة).
- **Role** — الأدوار (`key` فريد مثل `super_admin`، أسماء عربية/إنجليزية، علامة `isSystem` للأدوار المحمية).
- **RolePermission** — ربط دور بمفاتيح الصلاحيات (علاقة كثير-لكثير، حذف متسلسل مع الدور).
- **Setting** — إعدادات عامة بقيمة مفتاحية (اللغة، علامة التهيئة...).
- **Department** — الأقسام (كود فريد، الاسم، نسبة بدل طبيعة العمل اختيارية).
- **Employee** — الموظفون (كود فريد كمفتاح طبيعي للاستيراد، بيانات الهوية والعمل، القسم، نوع التعاقد، ملف العمل الذي يُحفظ ويُعرض باسم `<code>_<name>.<ext>`، وربط إعادة التعيين `rehiredFromId`).
- **EmployeeStatusHistory** — السجل التاريخي للحالات: كل انتقال (من/إلى) مع السبب ومستخدم المنفّذ والتاريخ.
- **Leave** — الإجازات (الموظف، النوع، الفترة، الأيام، السنة، الحالة، المستند الموثق).
- **PayrollBatch** — ملف كشف PDF (نوع، شهر، سنة، الاسم المحفوظ، عدد الصفحات)، وعلامتا `departmentsScanned` و`absencesScanned` تبيّنان هل فُحص القسم وأيام غياب هذا الكشف.
- **PayrollEntry** — ظرف موظف: دفعة (مرتب/حافز/أخرى) مع الأساسي والاستحقاقات والاستقطاعات والصافي ورقم الصفحة في الكشف، وأيام الغياب (بإذن/بدون إذن) المقروءة من رأس ظرف الحافز.
- **PayrollItem** — بند مفردات من ظرف المرتب/الحافز (النوع `earning/deduction`، اسم البند، مفتاح موحّد للتجميع `labelKey`، القيمة، والرصيد المستحق على السلف) مرتبط بـ `PayrollEntry` Cascade — منه تُبنى مصفوفة «مفردات الشهر».
- **ContractType** — كتالوج أنواع التعاقد (دائم، مؤقت، موسمي…)؛ الموظف يحمل `contractTypeId` + لقطة اسم تعاقده.
- **BasicSalaryGrade** — تدرج الأساسي: تاريخ السريان، القيمة، الملاحظات، ومستند استحقاق اختياري (PDF/Excel).
- **DepartmentTransfer** — التنقلات بين الأقسام (من → إلى، الفترة، ملاحظة، قرار موثق اختياري) — يُبنى تلقائيًا من كشوف المرتبات.
- **IncentiveRateBatch / DepartmentIncentiveRate** — نسب الحوافز الشهرية لكل قسم (تاريخ كامل): النسبة المتغيرة كل شهر + المستند المُرفوع (ملف «نسب الأقسام-الشهر.pdf») للمعاينة.
- **EmployeeIncentiveRateBatch / EmployeeIncentiveRate** — نسب الحوافز الفردية الشهرية لكل موظف (من ملف «نسب الحوافز الفردية-الشهر.pdf»): تطابق بالكود ثم الاسم، مع المستند للمعاينة.
- **EmployeeIncentivePenaltyBatch / EmployeeIncentivePenalty** — الحرمان من الحافز شهريًا لكل موظف: نسبة الخصم وقيمته (من ملف «الحرمان من الحافز-الشهر.pdf») + المستند للمعاينة.

### مسار قاعدة البيانات

تُخزَّن في `app.getPath('userData')/hr-system.db` — أي **خارج مجلد التطبيق**، فتبقى محفوظة بعد التحديثات ولا تُفقد عند إعادة التثبيت.

### آلية التهيئة (لماذا لقطة DDL؟)

التطبيق المُغلَّف لا يستطيع تشغيل `prisma migrate` (محرّكات Prisma غير مضمّنة بالكامل في حزمة Electron). لذلك:

1. `npm run prisma:snapshot` يولِّد `electron/main/db-snapshot.ts` — لقطة DDL خام بصيغة SQLite من المخطط.
2. عند أول تشغيل، `electron/main/prisma.ts` يطبِّق هذه الـ DDL مباشرة على قاعدة البيانات الجديدة.
3. بعدها يعمل `seed.ts` لإنشاء الأدوار الأساسية وحساب المدير.

الجداول الجديدة تُنشأ تلقائيًا حتى على قاعدة بيانات سابقة (`CREATE TABLE IF NOT EXISTS`)، والأعمدة الجديدة في جدول موجود تُضاف عبر سلسلة `SCHEMA_UPGRADES` (أوامر `ALTER TABLE`) في `electron/main/prisma.ts` — كل ذلك عند الإقلاع وبصيغة Idempotent آمنة.

> **بعد أي تعديل على `schema.prisma`:** شغِّل `npm run prisma:snapshot` لتحديث لقطة DDL، وارتِقِ برقم إصدار التطبيق في `package.json` لتطبيق الترقية على قواعد البيانات الموجودة. توليد عميل Prisma يتم تلقائيًا عند `npm run dev` أو `npm run build` (عبر `scripts/prisma-ensure.mjs`)، فلا داعي لتوليده يدويًا بعد الآن.

## الاستيراد والتصدير

وحدتا **الموظفون** و**الأقسام** تستوردان ملفات Excel (`.xlsx/.xls/.csv`) أو PDF عبر شاشة الاستيراد، مع معاينة الصفوف وتعديلها قبل التأكيد. المطابقة على عناوين الأعمدة بالعربية والإنجليزية، مع تسامح في التشكيل وعلامات الاتجاه (bidi) وصيغ التواريخ.

### أعمدة استيراد الموظفين

| العمود في الملف (مرادفات مقبولة) | مطلوب | الحقل |
|---|---|---|
| كود الموظف / رقم الموظف | نعم | `code` |
| اسم الموظف | نعم | `name` |
| الرقم التأميني، الرقم القومي، الدرجة، التواريخ، المؤهل، سنة المؤهل | لا | الاسم نفسه بالإنجليزية |
| رقم القسم / كود القسم | لا | `departmentCode` |
| اسم القسم / القسم | لا | `departmentName` |
| نوع التعاقد | لا | `contractType` |

**قاعدة الأعمدة الاختيارية (القسم ونوع التعاقد):**

- العمود غايب من الملف ⟵ ما هو محفوظ للموظف يبقى كما هو؛ إعادة الاستيراد **لا تصفّر** قيماً موجودة.
- القسم يُطابَق **بالكود** أولاً ثم **بالاسم**، ويُنشأ قسم جديد تلقائياً إذا لم يوجد في قاعدة البيانات.
- الموظف الجديد يُسجَّل بالقيم الواردة، وتبقى `null` إذا لم ترد.

الحفظ يتم في `electron/main/import/employeesPersist.ts` داخل معاملة واحدة (ينجح الاستيراد كله أو لا شيء).

### تعبئة أعمدة ناقصة من ملف جاهز

لو الموظفون مسجّلون بالفعل وعندك ملف يحمل القسم ونوع التعاقد:

```bash
node scripts/update-employee-dept-contract.mjs              # معاينة فقط (لا يكتب شيء)
node scripts/update-employee-dept-contract.mjs --apply      # تنفيذ
node scripts/update-employee-dept-contract.mjs --apply "D:\path\to\file.xlsx"
```

يقرأ `Desktop/بيانات الموظفين.xlsx` افتراضياً، يطابق بالكود، يملأ الحقول الفارغة فقط، وياخذ نسخة `.bak` بجانب قاعدة البيانات قبل أي كتابة.

### التصدير (PDF / Excel)

زر **تصدير** في تبويبات الموظفين والأقسام و**الإجازات** والإجازات والمرتبات والتنقلات يصدّر **القائمة الحالية كما هي** — بنفس الفلاتر والترتيب المطبقين — بخمس صيغ:

- **تقرير PDF** (`electron/main/export/report.ts`): صفحة A4 (أفقية إذا زادت الأعمدة عن 7) مع رأس داكن/ذهبي، رأس جدول يتكرر على كل صفحة، وخط عربي سليم — يُولَّد عبر `webContents.printToPDF` في نافذة خفية، فلا حاجة لمكتبات PDF خارجية.
- **ورقة Excel** (مكتبة `exceljs`): ورقة RTL مع تثبيت رأس الجدول، وفلتر تلقائي، وعرض أعمدة، وتظليل متناوب، وتنسيق أرقام للنسب.
- **مستند Word**: يُكتب HTML متوافق بامتداد `.doc` يفتحه وورد مباشرة محافظًا على الاتجاه والتنسيق.
- **صورة PNG**: لقطة عالية الدقة للتقرير عبر `capturePage` في نافذة خفية (تكبير 150%).
- **طباعة**: حوار طباعة النظام على التقرير نفسه (ومنها الحفظ كـ PDF).

التصدير محمي بصلاحية العرض (`employees.view` / `departments.view` / `leaves.view`)، ويُفتح معه نافذة اختيار مسار الحفظ (الافتراضي: مجلد المستندات)، والتواريخ تُصدَّر بصيغة ISO `yyyy-mm-dd` ليبقى الملف قابلًا للفرز والفلاتر في Excel.

## ملف الموظف (دوسييه)

كل موظف له صفحة `/employees/:id` (تفتح من «الملف الكامل» في قائمة الموظفين — قائمة الصف) تجمع كل ما يخصّه في مكان واحد:

- **تبويبات:** البيانات، ملف العمل، الإجازات، الرواتب.
- **حالة الموظف الوظيفية مع سجل تاريخي:** كل موظف له حالة (نشط، إجازة بدون مرتب، محال للمعاش، متوفى، مستقيل، منتهي خدمته، موقوف) تتغير من «إدارة الحالة» مع سبب اختياري، وكل انتقال يُسجَّل في خط زمني (من → إلى، السبب، المستخدم، التاريخ). `isActive` مشتقة تلقائيًا من الحالة فلا تتعارض عندهما أبدًا.
- **المعاش والعقود الجديدة:** يُعرض تاريخ بلوغ سن المعاش القانوني (60 عامًا) في تبويب «سجل الحالة»، وعند بلوغه يُحوَّل الموظف **تلقائيًا** إلى «محال للمعاش» (ومَن خرج ومتى يظهر في تبويب **المعاشات** بشاشة المراجعة) مع تسجيل الانتقال في السجل (المنفذ: النظام). زر **«عقد جديد (إعادة تعيين)»** ينشئ ملف موظف جديد بنفس البيانات الشخصية للملف الحالي (الذي يبقى كما هو بحالته) مع رقم موظف مختلف ونوع تعاقد جديد (من كتالوج أنواع التعاقد) وتاريخ تعيين، وشارتان في رأس الملف تربطان الملفين وتنقّلان بينهما. وإن أُضيف الموظف كملف جديد منفصل، زر **«ربط بملف سابق»** يربطه بملفه الأصلي ويكمل فراغاته فقط دون المساس بحالة الملف القديم وسجله (ظروف ما قبل المعاش)، مع سكربت `reconcile-rehires.mjs` للتسوية الجماعية بدرجات ثقة.
- **كتالوج أنواع التعاقد:** نموذج الموظف يختار نوع العقد من قائمة مركزية تُدار بالكامل (إضافة/تعديل/حذف) عبر نافذة «أنواع التعاقد» — تُزرع بالقائمة الافتراضية وفق قانون العمل المصري وتلتقط أي أسماء قديمة موجودة، وحذف نوع يُحرر الربط فقط دون المساس بأسماء العقود المحفوظة لدى الموظفين.
- **التبويبات القادمة** (حضور وانصراف، تقارير) مسجلة في هيكل الصفحة وتظهر بحالة «قريبًا» — إضافة وحدة مستقبلية لا تتطلب إعادة تصميم.
- **الإجازات تُدار من الملف نفسه** (إضافة/عرض/تعديل/حذف مع المستند الموثق) مع شريط ملخص (الإجمالي، الموافق، قيد الانتظار، الأيام).
- ملف العمل يُعرض ويُدار بنفس نافذة وحدة الموظفين (`EmployeeFileModal`)، وكل تحديث ينعكس فورًا على القوائم. يُحفظ الملف باسم مشتق من الموظف للتنظيم: `<كود الموظف>_<اسم الموظف>.<الامتداد>` (مثال `2689_أحمد عبد القادر.pdf`) عبر `buildStoredName()` في `electron/main/employee-files.ts`، ويُعرض الاسم نفسه في الواجهة بجانب المرفق بدلًا من اسم الملف الأصلي.

## الأجور والمرتبات

تبويب **الأجور والمرتبات** (`/payrolls`) يستقبل كشف الرواتب PDF ويوزّعه تلقائيًا على الموظفين:

- **الرفع والتوزيع:** زر «رفع كشف PDF» → اختيار الملف (مثل `مرتب شهر 092026.pdf` أو `حافز 092026.pdf`) → المحلّل (`electron/main/payroll-parser.ts`) يستخرج **ظرف كل موظف من صفحة مستقلة**: رقمه (بجانب «الرقم» أو بعد «إجمالي الاستقطاعات»)، اسمه، الأساسي، إجمالي الاستحقاقات، الاستقطاعات، والصافي — مع مطابقة تلقائية بالكود ثم بالاسم داخل شاشة معاينة توضح المطابق/غير المطابق قبل التأكيد. الجدول يعرض **كل موظف مرة واحدة** (كود/اسم/قسم/عدد الدفعات) ولا يزاحم بأعمدة الشهر والماليات.
- **النوع والشهر يُستنتجان من اسم الملف** (`shared/payrolls.ts`): حافز/مرتب/أخرى + الشهر/السنة (`092026` → 09/2026). رفع نفس الشهر والنوع يستبدل النسخة السابقة فقط.
- **المعاينة:** بوب أب واحد يتيح اختيار **نوع المرتب** (مرتب/حافز/أخرى) و**الشهر** لكل موظف، فيتعرض ظرفه الأصلي (تقطيع بـ `pdf-lib`) بجانب الأرقام المستخرجة (أساسي/استحقاقات/استقطاعات/صافي والكشف المصدر) — من تبويب «الرواتب» في ملف الموظف، أو من قائمة الموظفين (بند «المرتبات»)، أو من داخل القائمة نفسها، مع تصدير PDF/Excel يفصّل كل الدفعات.
- **التخزين:** الكشف الأصلي يُحفظ مرة واحدة في `<Documents>/HR-System/PayrollFiles` (بدون تكرار) وتُحذف مع آخر دفعة له، وتُرصد الأرقام في `PayrollBatch`/`PayrollEntry`.

**تدرج الأساسي:** داخل «الرواتب» لكل موظف — سجل بتاريخ/قيمة/ملاحظات لكل تغيير في الأساسي (زيادة سنوية، قرار…)، مع إضافة/تعديل/حذف وإرفاق مستند استحقاق PDF أو Excel (معاينة PDF أو جدول Excel) في `<Documents>/HR-System/SalaryGradeFiles`.

**التنقلات بين الأقسام:** تبويب «التنقلات» في الملف الكامل يعرض سجلًا تاريخيًا (من قسم ← إلى قسم، من/إلى التاريخ، ملاحظة) مع **القرار الموثق** — رفعه اختياري وتظهر شارة «لا يوجد قرار» لاستيفائه. عند رفع كشوف المرتبات يتم **مطابقة اسم القسم في الظرف مع تبويب الأقسام** (أطول اسم مطابق، ‏95%+ من الأظرف) فيُحدَّث القسم الحالي تلقائيًا ويُسجَّل التنقل (يُقفل السابق ويُفتح الجديد من أول الشهر) في `<Documents>/HR-System/TransferDecisionFiles`. **الردّ التاريخي:** عند الإقلاع يُعاد فحص أي كشوف مخزنة لم تُفحص بعد بالترتيب الزمني (كشف المرتب هو مرجع الشهر، وتُتجاهل المصادر المتضاربة من نفس الشهر) وتُبنى التنقلات من أول كشف — طبّقناها على الكشوف الخمسة الحالية (‏05→09/2026) فأنتجت 380 تنقلًا لـ301 موظفًا وحدّثت الأقسام الحالية (مثال: ‏2689 = ورش الأعمد→دهان الوصلات→ورش الأعمد→الصب الأرضي). السجل يُطبع ويُصدَّر بـ **PDF/Excel/Word/صورة/طباعة** مع ذكر رقم واسم الموظف في رأس التقرير (مثال: `[2689] أحمد عبد القادر…`).

## المراجعة ومفردات الأجر

تبويب **المراجعة** (`/reviews`) شاشة تفتيش شهرية بثلاثة أقسام (**مفردات المرتب والحافز** و**الغيابات** و**المعاشات**). تبدأ بمصفوفة **مفردات المرتب والحافز**: اختيار النوع (مرتب/حافز) والشهر يُظهر **صفًا لكل موظف** و**عمودًا لكل بند** من بنود مفردات ظرفه.

- **استخراج المفردات:** يُقرأ كل ظرف (صفحة من كشف الـPDF) من **مواضع عناصر النص (x/y)** داخل الصفحة: تُجمَّع العناصر في أسطر، وتُحدَّد أعمدة الجدول من صف العنوان (`الرصيد | القيمة | الاستقطاعات | القيمة | الاستحقاقات`)، فتُربط كل قيمة بسطرها (نفس السطر لا عمود جارٍ) وتُتجاهل صفوف الإجماليات والصافي (محسوبة أصلًا في `PayrollEntry`). المحلّل: `electron/main/payroll-items.ts` — يوحّد شكل النص (تشكيل/تطويل/حروف متبدّلة) ويصلح انعكاس الأقواس الناتج عن اتجاه الصفحة، وله مسار احتياطي بخلايا الجدول المكتشَف (`pdf-parse` → `getTable()`).
- **التخزين:** كل بند صف في `PayrollItem` (النوع `earning/deduction`، اسم البند، مفتاح موحّد للتجميع `labelKey`، القيمة، والرصيد المستحق على السلف) مرتبط بـ `PayrollEntry` Cascade. الاستخراج يجري **تلقائيًا عند استيراد كشف جديد**، فلا حاجة لأي إجراء يدوي؛ ولا يظهر زر «استكمال استخراج المفردات» في الشاشة إلا إذا كان في الشهر أظرف لم تُستخرج مفرداتها (كشف قديم أُضيف قبل هذه الميزة) مع بيان عددها، فيبقى كل زر له عمل حقيقي. وبقراءة مواضع العناصر بدل خلايا الجدول تُربط كل قيمة بسطرها الصحيح — لأن خوارزمية الجداول تُسند بعض الصفوف (مثل صفّ مكافأة التشجيعية) إلى خلايا مزاحة؛ وبهذا يطابق مجموع البنود **إجماليات الـPDF المطبوعة في 3,391 من 3,394 ظرفًا** (الباقي أظرف ناقصة أو فيها مديونية سابقة).
- **المصفوفة (مبسّطة للقراءة):** الجدول يعرض ستة أعمدة فقط — **الكود** و**الاسم** و**القسم** و**إجمالي الاستحقاقات** و**إجمالي الاستقطاعات** و**الصافي** — بلا تمرير أفقي وبلا أعمدة بنود كثيرة؛ والنقر على إجمالي الاستحقاق أو الاستقطاع يفتح نافذة تعرض بنود الموظف تفصيلًا (بند/قيمة) مع مجموعها ورصيد سلفه. البنود نفسها تبقى في قاعدة البيانات وفي ملف التصدير (PDF/Excel/Word/صورة/طباعة) بأعمدتها الكاملة، مع صف إجمالي لكل عمود، وبحث بالاسم أو الكود وفلتر بالقسم.
- **الرصيد:** عمود «الرصيد» في الظرف هو رصيد السلفة المستحق على الموظف (لا بند مرتب)، فيُربط ببند السلفة في سطره ويظهر في نافذة التفاصيل، ولا يظهر كعمود مستقل في الجدول حتى لا يختلط بالبنود.
- **الحجم:** الكشوف الحالية (11 كشفًا = 3,394 ظرفًا) تُستخرج منها 38,966 بندًا خلال ~35 ثانية بسكربت `scripts/backfill-payroll-items.mts` (يعمل مرة واحدة على الفاتر القديمة) — والسكربت نفسه يملأ **أيام الغياب** على أظرف الحافز (70 ظرفًا في الكشوف الخمسة الحالية). أما الكشف الذي يُستورد بعدًا فتُقرأ أيام غيابه تلقائيًا عند الاستيراد، وتبقى الأولوية لردّ الفحص عند الإقلاع.
- **تقرير الغيابات (بالأيام):** قسم **الغيابات** في نفس شاشة المراجعة (زر في شريط الأقسام) يعرض **من غاب عن شهر الحافز** و**كم يومًا** — جدول بأعمدة: الكود/الاسم/القسم/**غياب بإذن (أيام)**/**غياب بدون إذن (أيام)**/**إجمالي الأيام**، مرتَّب بالأشدّ أولًا، مع ملخّص (عدد الغائبين وإجمالي الأيام) وفلتر بالقسم وبحث بالاسم أو الكود وتصدير بصيغ مصفوفة المفردات. الأيام **ليست مبالغ**: تُقرأ من **رأس ظرف الحافز** («غياب بدون اذن:- ٨» و«غياب باذن:- ٠٫٥») وتُخزَّن على `PayrollEntry` في `absenceWithPermissionDays` و`absenceWithoutPermissionDays`؛ أما في ظرف المرتب فـ«غياب بدون اذن» **مبلغ** ضمن بنود الجدول لا عدد أيام — لذلك يقتصر القراءة على السطور **فوق** رأس جدول البنود (`readAbsenceDays()` في `electron/main/payroll-items.ts`)، والتصنيف على `labelKey` المُطبَّع في `classifyAbsenceField()` فيتحمّل اختلاف الإملاء («غياب باذن»/«غياب بأذن»/«غياب بدون إذن») ويقرأ القيمة من يسار التسمية في السطر نفسه (اتجاه صفحة الـPDF من اليمين لليسار). ولأن الموظف له ظرفان في الشهر (مرتب وحافز) ولكلٍّ قسمه المستنتج من نصّه، **تُؤخذ بيانات الموظف من الظرف الذي يحمل أيامه** (الحافز) لا من ظرفه الآخر.
- **حالة فحص الغيابات (لن يفرغ التقرير صامتًا):** كل كشف يحمل علامة `absencesScanned` تبيّن أنه فُحصت أيام غيابه. وأيام الغياب **مشتقّة من الملف** ولا تُكتب إلا عند الفحص، فبلا العلامة كان التقرير يُظهر «لا يوجد غياب» بينما الحقيقة أن الأيام لم تُقرأ بعد. لذلك: (1) **ردّ الفحص عند الإقلاع** — `backfillPayrollAbsences()` في `electron/main/payroll-absences.ts` يفحص كل كشف لم تُفحص أيامه (كشف أُضيف قبل الميزة، أو كشف استُعيد من نسخة احتياطية قديمة) ويعيد بناء الأيام، وهو يعمل **بعد فتح النافذة** فلا يعطّل الإقلاع؛ (2) **حالة صريحة في التقرير** — تُرجع `AbsencesReport` الحقول `scanned` و`scannedBatches` و`totalBatches` و`missingFiles`، فإذا بقي كشف لم يُفحص ظهر شريط تنبيه يشرح السبب بدل جدول فارغ، مع زر «استخراج أيام الغياب» (صلاحية `payrolls.create`)؛ (3) **تحديث دوري** — ما دام الفحص جاريًا تُحدَّث الشاشة كل 3 ثوانٍ (`refetchInterval`) فينعكس الفحص فور انتهائه؛ (4) الملفات المفقودة من الأرشيف تُذكر بالاسم في التنبيه بدل أن تختفي. النتيجة على الكشوف الحالية: **70 ظرفًا** بأيام غياب (من أظرف الحافز فقط — كشف المرتب يُقرأ منه صفرًا لأن «غياب بدون إذن» فيه مبلغ لا أيام).

- **تقرير المعاشات:** قسم **المعاشات** في شاشة المراجعة يعرض **المحالين للمعاش** بجدول: الكود/الاسم/القسم/تاريخ الميلاد/**تاريخ المعاش**/نوع الإحالة (تلقائي أو يدوي)، مع بطاقات ملخّص (عدد المحالين، عدد السنوات، آخر معاش) وتصدير بصيغ مصفوفة المفردات. **تاريخ المعاش** هو تاريخ بلوغ السن القانونية محسوبًا من تاريخ الميلاد (`retirementDateOf` في `shared/employeeStatuses.ts`) لأنه التاريخ الحقيقي للإحالة ويصلح للتجميع — أما تاريخ تسجيل الحالة في السجل فهو وقت اكتشاف النظام لها (وقد يكون يومًا واحدًا لكل الموظفين القدامى عند أول تشغيل)، فلا يصلح للتجميع. ولذلك يعمل فلتر **السنة** على هذا التاريخ: كل سنة تظهر بعدد الخارجين فيها (`2026 (17)`)، واختيار سنة يتيح فلتر **الشهر** بأعداد كل شهر فيها، فيُعرف من خرج في كل شهر. ومن لا تاريخ ميلاد له (إحالة يدوية) يُستخدم تاريخ تسجيل الحالة بدلًا منه، ويُوسم المصدر «يدوي» بدل «تلقائي». التحويل التلقائي يجري قبل بناء التقرير (`applyAutomaticRetirement`) فلا ينتظر فتح شاشة الموظفين. البناء والتجميع في `electron/main/retirements.ts`، والـ IPC في `retirements.ipc.ts` بصلاحية `reviews.view`.
- **الجداول الموحّدة:** كل جدول في التطبيق يمرّ من `DataTable` (`src/components/ui/DataTable.tsx`): منطقة تمرير بارتفاع محدود، **رأس ثابت** أثناء التمرير (`sticky top-0` مع ظل) وترويسة موحّدة (لون `bg-bg-700` + `border-line-strong` + حروف صغيرة)، وتذييل **إجماليات ثابت** في أسفل الجدول (`sticky bottom-0`) في شاشات المراجعة الثلاث. الشبكات المضغوطة داخل النوافذ (معاينة الاستيراد، نسب الحوافز، الجزاءات) تستعمل `dense` ليبقى صف الرأس وحجم الخط أصغر. أي جدول جديد يمرّ بالمكوّن نفسه فلا يختلف شكله عن البقية.

## الأمان والصلاحيات

نظام حماية مزدوج:

**الطبقة 1 — الـ main process (المصدر الموثوق):** كل IPC handler مُغلَّف بطبقة تتحقق من الجلسة والدور قبل تنفيذ أي عملية. لا يمكن تجاوزها من الواجهة.

**الطبقة 2 — الـ renderer (طبقة UX):** مكوِّن `<Protected permission="users.edit">`، حرس المسارات في React Router، وعناصر الـ sidebar تُفلتر حسب الصلاحيات (**إخفاء وليس تعطيل فقط**).

**منطق موحَّد:** `hasPermission(role, key)` مُصدَّر من `shared/permissions.ts` ويُستخدم في الطبقتين، فلا يمكن أن تختلف القاعدة بين الواجهة والخادم.

### مفاتيح الصلاحيات

```
users.view | users.create | users.edit | users.delete | users.manage_status
roles.view | roles.create | roles.edit | roles.delete
departments.view | departments.create | departments.edit | departments.delete | departments.import
employees.view | employees.create | employees.edit | employees.delete | employees.import | employees.manage_status | employees.manage_contract_types
leaves.view | leaves.create | leaves.edit | leaves.delete
payrolls.view | payrolls.create | payrolls.edit | payrolls.delete
reviews.view | reviews.create | reviews.edit | reviews.delete
settings.view | settings.edit
```

### الأدوار المُجهَّزة (seeded)

| الدور | الصلاحيات | ملاحظات |
|---|---|---|
| `super_admin` | تجاوز ضمني لكل الصلاحيات | لا يحتاج تعيين كل المفاتيح يدوياً |
| `hr_manager` | كل مفاتيح الصلاحيات عدا `roles.delete` | تُزامَن تلقائيًا مع الكتالوج عند كل إقلاع |
| `employee` | `settings.view` فقط | قاعدة للوحدات القادمة |

### الحمايات

- لا يمكن حذف `super_admin` ولا تعطيله (مرفوض من الـ main process نفسه).
- كلمات المرور تُخزَّن عبر `bcryptjs` بكلفة 10 — اخترنا النسخة JS الصافية لتجنب مشاكل التجميع (node-gyp) في Electron.
- الجلسة في ذاكرة الـ main process فقط (`auth:login` / `auth:logout` / `auth:me`).
- **قفل تسجيل الدخول:** بعد 5 محاولات فاشلة لنفس اسم المستخدم يُقفل تسجيل الدخول 30 ثانية (`TOO_MANY_ATTEMPTS`) — حماية من التخمين/القوة الغاشمة.
- **فحص توقيع الملفات:** أي رفع (ملف عمل موظف أو مستند إجازة) يُفحص بـ Magic bytes — PDF يبدأ بـ `%PDF-`، Excel حزمة ZIP، الصور بتوقيعاتها — فلا يُقبل ملف غُيّر امتداده فقط.
- **نظافة القرص:** حذف الموظف أو الإجازة يمسح الملف الفعلي من `Documents` قبل حذف الصف (بما يشمل مستندات الإجازات عند حذف موظف).
- `system:revealDatabase` يتطلب جلسة دخول نشطة (لا يُستدعى قبل تسجيل الدخول).

## التعدد اللغوي و RTL

- `react-i18next` + ملفا `ar.json` / `en.json` (كل النصوص بما فيها أسماء الأدوار ومصفوفة الصلاحيات).
- عند التبديل: `i18n.changeLanguage` → `document.dir = 'rtl'|'ltr'` → تبديل الخط → حفظ في جدول `Setting`.
- تُستخدم **CSS logical properties** (`ps-`, `pe-`, `ms-`, `me-`) و variants من Tailwind `rtl:`/`ltr:` لقلب الأيقونات والهوامش تلقائياً.
- **قاعدة صارمة:** لا قيم `left`/`right` صريحة في CSS — logical properties فقط.
- الافتراضي عربي RTL.

### لماذا `asar: false`؟

المعامل `asar` مُعطَّل في `electron-builder.yml` عمداً: حتى يتمكّن عميل Prisma (محرك `.node` الثنائي) من التحميل من مسار حقيقي بدلاً من أرشيف asar افتراضي.

### afterPack hook

سكربت `scripts/after-pack.cjs` ينسخ `node_modules/.prisma` (العميل المُولَّد) إلى داخل الحزمة، لأن electron-builder يحذفه باعتباره ليس حزمة npm حقيقية. بدون هذا، سيفشل التطبيق المُغلَّف في الاتصال بقاعدة البيانات.

- [ ] استعادة نسخة احتياطية: تُحفظ لقطة `pre-restore` بجانب القاعدة، وتُستعاد القاعدة والمستندات، ومعاينة مستند حافز تعمل بعد الاستعادة.
- [ ] تبويب **المراجعة**: اختيار «مرتب» أو «حافز» ثم الشهر يُظهر جدولًا بستة أعمدة (الكود/الاسم/القسم/إجمالي الاستحقاقات/إجمالي الاستقطاعات/الصافي) بلا تمرير أفقي، والترويسة تبقى ثابتة عند التمرير، والنقر على إجمالي الاستحقاق أو الاستقطاع يفتح نافذة ببنود الموظف ومجموعها.
- [ ] قسم **الغيابات** في المراجعة: اختيار شهر الحافز يُظهر **أيام** الغياب (لا المبالغ) بأعمدة (الكود/الاسم/القسم/غياب بإذن/غياب بدون إذن/إجمالي الأيام)، والأيام الكسرية (نصف يوم) تظهر كـ«0.5» لا كصفر.
- [ ] استيراد كشف جديد → تُستخرج مفرداته تلقائيًا (لا زر «استكمال» يظهر)، ويلتزم مجموع بنود الموظف بإجمالي الاستحقاق المطبوع على ظرفه.
- [ ] **الرؤوس الثابتة:** في كل شاشات القوائم (الأجور والمرتبات، الموظفون، الأقسام، الإجازات، المستخدمون) يبقى رأس الجدول ظاهرًا عند التمرير داخل الجدول، وكذلك في جداول النوافذ (معاينة الاستيراد، نسب الحوافز، الجزاءات).

## إضافة وحدة جديدة

النظام مصمم ليكون قابلاً للامتداد. لإضافة وحدة (مثلاً "الموظفون"):

1. **الصلاحيات:** أضف مفاتيح الوحدة إلى `MODULE_PERMISSIONS` في `shared/permissions.ts` (هذا هو المصدر، كل المستهلكين يُشتقون منه).
2. **الـ main:** أضِف `employees.ipc.ts` مع تجميع كل handler بالصلاحيات المناسبة، وسجِّله في `ipc/index.ts`.
3. **الـ preload:** أضِف الدوال إلى `window.api` في `electron/preload/index.ts` مع الأنواع.
4. **الواجهة:** أنشئ `src/modules/employees/` (قائمة + نماذج)، أضِف مساراً محمياً في `App.tsx`، وعنصراً في `src/components/layout/nav.ts` (يُفلتر تلقائياً حسب الصلاحية).
5. **قاعدة البيانات:** عدِّل `prisma/schema.prisma` → `npm run prisma:snapshot`. توليد عميل Prisma تلقائي مع `npm run dev` / `npm run build`.
6. **المستندات:** أي وحدة تخزّن ملفات على القرص تُضيف مجلدها إلى `DOCUMENT_FOLDERS` في `electron/main/document-folders.ts` وتستدعي `getDocumentFolderDir()`، فيُشمَل المجلد تلقائيًا في النسخ الاحتياطي/الاستعادة.
7. **اللغات:** أضِف الترجمات إلى `ar.json` و `en.json`.

## استكشاف الأخطاء

| المشكلة | السبب والحل |
|---|---|
| خطأ "Prisma did not produce any DDL" | شغِّل `npm run prisma:generate` أولاً، تأكد من صحة `schema.prisma` |
| شاشة فارغة رغم وجود بيانات (أو خطأ "Unknown argument" من Prisma) | عميل Prisma المُولَّد أقدم من `prisma/schema.prisma` — شغِّل `npm run prisma:ensure` (أغلق التطبيق أولًا، فهو يقفل محرّك SQLite) |
| شاشة «المراجعة» بلا بنود رغم وجود أظرف | المفردات لم تُستخرج بعد — استخدم زر «استخراج المعلَّق» في الشاشة نفسها، أو `node scripts/backfill-payroll-items.mts` |
| تقرير الغيابات فارغ رغم وجود غياب في أظرف الحافز | أيام الغياب لم تُفحص بعد — انظر شريط التنبيه في تبويب الغيابات واضغط «استخراج أيام الغياب»، أو `npm run payrolls:backfill`. الفحص يجري تلقائيًا عند الإقلاع لكل كشف لم تُفحص أيامه. |
| تقرير المعاشات لا يعرض موظفًا تجاوز السن القانونية | الموظف بلا تاريخ ميلاد فلا يُحسب له سن معاش — أضف تاريخ الميلاد من ملفه، أو أحِلْه يدويًا من «سجل الحالة» فيظهر بتاريخ التسجيل ويُوسم «يدوي» |
| التطبيق المُغلَّف لا يتصل بقاعدة البيانات | `node_modules/.prisma` غير منسوخ — تأكد أن `scripts/after-pack.cjs` يعمل (توليد العميل تلقائي قبل `build:win`) |
| فشل تجميع bcrypt | المشروع يستخدم `bcryptjs` (JS صافٍ) — لا تستبدله بـ `bcrypt` الذي يحتاج node-gyp |
| بطء في blur/3D | حصر `backdrop-filter` على عناصر محدودة + استخدم `will-change` باعتدال |
| RTL يكسر التخطيط | توجد قيمة `left`/`right` صريحة — استبدلها بـ logical properties |
| فقدان DB بعد التحديث | تأكد أن قاعدة البيانات في `userData` وليست داخل مجلد التطبيق |
| أزرار الاستيراد/التصدير لا تعمل في النسخة المُغلَّفة | تبعيات التشغيل (`xlsx` / `pdf-parse` / `exceljs`) ليست داخل الحزمة — يجب أن تتضمن `files` في `electron-builder.yml` كل `node_modules/**/*` (devDependencies تُستبعد تلقائياً) |
| بعد التحديث لا تظهر جداول/أعمدة جديدة (مثل جدول الإجازات أو عمود الحالة) | أعد تشغيل التطبيق مرة واحدة — يُطبَّق DDL `CREATE TABLE IF NOT EXISTS` وأوامر `ALTER` في `electron/main/prisma.ts` عند الإقلاع تلقائيًا |
| رفض ملف صحيح الشكل عند الرفع | المحتوى لا يطابق الامتداد (فحص Magic bytes) — أعد التصدير بالصيغة الصحيحة من المصدر |
| التطبيق ينهار فور الإقلاع بـ `Cannot read properties of undefined (reading 'isPackaged')` | المتغير `ELECTRON_RUN_AS_NODE=1` في البيئة يجعل Electron يعمل كـ Node عادي فيضيع `app` — `electron.vite.config.ts` يحذفه تلقائيًا قبل التشغيل، فإن أصرّ الخطأ فامسح المتغير من بيئة الطرفية |
| رسالة «محاولات كثيرة» في تسجيل الدخول | نظام الحماية: 5 محاولات فاشلة = قفل 30 ثانية لنفس اسم المستخدم — انتظر ثم أعد المحاولة |
